# ADR 0018 — Multi-agent (S14): sub-agent delegation and handoffs over ordinary runs

Status: accepted (planning ADR — no S14 code exists at time of writing)
Date: 2026-09-15
Supersedes: none (implements the roadmap S14 sketch; scope confirmed by
Harshit 2026-09-15 — handoffs are IN v1, not deferred)

## Context

Everything through S13 executes one agent loop per run, with agents
reaching outward only to tools and MCP servers. The roadmap S14 sketch
calls for agents deleg to agents — supervisor/handoff patterns — riding
the tool family (an agent is "just another tool", the S4 pattern) and
`ExecutionContext`. This ADR pins that design.

## Decision

### 1. One dynamic tool family: `sub__<agent-name>` and `handoff__<agent-name>`

A supervisor binds sub-agents as ordinary `ToolBinding`s with names
minted by a new `SubAgentToolProvider` (mirroring `McpToolProvider`):

- Binding `config` carries `{agent_id, agent_version_id}`. **The pin is
  server-stamped at parent publish time** — the `PATCH /v1/agents/{id}`
  route overwrites `config.agent_version_id` for every `sub__` /
  `handoff__` binding with the target's latest published version
  (the `_pin_agent_versions` pattern, D42 transposed to agents), 422
  when the target has no published version or is not visible to the
  tenant. The client NEVER supplies a pin (`AgentUpsertRequest.tools`
  is client-controlled free-form config — the route overwrites, never
  trusts). Stale pins (target republished since) surface as a lint list
  on the agent detail, never a failure — versions are immutable (D1),
  the pin still replays exactly what it pinned.
- **Publish-time cycle detection**: the route walks the new snapshot's
  `sub__`/`handoff__` bindings → pinned version snapshots → their
  bindings (Kahn's over immutable snapshots) and 422s on a cycle or
  direct self-binding. Structural note: with pins always
  latest-at-publish and versions immutable, the pin graph is acyclic
  by construction — the check is defense-in-depth (it survives any
  future relaxation of the overwrite rule); the runtime depth cap
  (§5) is the second belt.
- The binding NAME is display-only; identity resolves from
  `config.agent_id` (agent names are arbitrary strings — never parse
  the `sub__` suffix).
- **Provider composition**: an agent mixing `mcp__*` and `sub__*` /
  `handoff__*` bindings resolves ONE merged tooling (registry +
  `ToolRuntime` + `aclose`) — `_resolve_tooling` composes both
  providers instead of MCP alone. Resolution failures raise the new
  `SubAgentResolutionError`; `tools/mcp/errors.py` gains a shared
  `ToolResolutionError` base (McpResolutionError re-bases; the three
  catch sites — `AgentRuntime.run`, `AgentRuntime.resume`,
  `WorkflowRuntime.run` — catch the base). Resolution is eager per
  parent segment inside the try (D38, fifth application): a missing or
  foreign-tenant sub-agent is the parent's persisted terminal
  `run.failed` `error_kind="tool"` naming the agent, before a token.
- `SubAgentToolProvider.resolve(bindings, ctx)` receives the FULL
  `ExecutionContext` (not the MCP signature's tenant/principal pair):
  the tools need the parent's `run_id`, `trace_id`, `deadline`,
  `principal`, and depth at construction. This is provider-level, not
  a port — `McpToolProvider` is not in `ports/`, and neither is this.
- Descriptors mint with `annotations={"requires_approval": False,
  "timeout": -1}` (never approval-gated; §5 unbounded). Handoff
  descriptors additionally declare a single optional `note` argument.

### 2. Child runs are ordinary durable queue runs; the tool blocks on the child's stream

The `sub__` tool does not run the child in-process. At call time it:

1. **Enqueues the child** through the eval-children composition:
   pre-generated run_id, `queue_message` + `create_queued_run` one
   transaction (ADR 0008 §2), `kind="agent"`, shared `trace_id`,
   `parent_run_id` (§3), the PARENT's absolute `deadline` (survives
   the hop and bounds the child's own loop), parent
   principal/tenant/`session_id=None`, and metadata
   `{"sub_agent": {"depth": n}}` + the non-interactive flags (§5).
   The child is claimed, run, and finalized by the UNCHANGED worker —
   "nested runs must survive process death like any run" is literally
   the S1 queue contract.
2. **Blocks on `PgEventStream.subscribe(child_run_id)`** until the
   child's terminal event, checking `ToolContext.cancel` between
   batches. Subscribe works on a just-enqueued row (verified), and the
   parent worker's independent heartbeat keeps the lease alive
   throughout. Three endings besides the terminal:
   - **cancel observed** → `queue.request_cancel(child_run_id)` then
     re-raise `ExecutionCancelled` — the parent terminal-cancels; the
     child cancels at its own checkpoints.
   - **stream ends without a terminal** (defense-in-depth: a paused
     child should be impossible per §5, but `end_on_pause_status=True`
     also ends at a pause frame) → `request_cancel(child)` + an
     honest error `ToolResult`.
   - **the parent's deadline passes while waiting** → `request_cancel`
     + error ToolResult; the parent's next checkpoint fails it on
     deadline. This bound is REQUIRED: the sweeper only reaps expired
     leases, never pending queue rows — an unclaimed child message
     would otherwise block the parent forever (the single most
     likely production failure of this design, closed by design).
3. **Maps the child's terminal event**: `run.completed` → the child's
   `final_message` as the tool output; `run.failed` → `is_error=True`
   recoverable result carrying the child's error (the model may
   retry or continue); `run.cancelled` → re-raise so the parent
   cancels too. Usage is read off the TERMINAL EVENT (`RunCompleted`
   carries `total_usage`) — race-free by construction, unlike a row
   read racing `finish_run`.

**Crash semantics, accepted and recorded**: a parent worker crash
mid-child → the sweeper terminal-fails the parent (one
`run.failed`); the child is an independent claim that runs to
completion and acks — its result is orphaned but the run is fully
visible, resumable-forever, and linked (§3). This is the durability
win of queue-backed children; an in-process child was REJECTED (the
child row would be stuck RUNNING with no sweeper story).

### 3. Parent linkage: one additive envelope field + one column + the pre-declared port changes

- **Envelope**: `_Event` (ADR 0003, frozen) gains
  `parent_run_id: str | None = None` — the D43 `node_id` precedent,
  backward compatible in both directions (old rows replay as None;
  the same single-restart rolling-deploy discipline as S6). There is
  NO event factory — events are constructed inline at ~25 sites —
  so the stamp happens at ONE choke point: `InProcessEventSink`
  gains an optional `parent_run_id`, stamps in `_append` (it already
  mutates `sequence` there), and `worker._execute_claimed`
  constructs it from `message.parent_run_id`. The parent's own
  sweeper-written terminal carries `parent_run_id=None` — fine, the
  field is optional.
- **Row**: `agent_executions` gains nullable `parent_run_id` +
  index (migration 0012). A real column, not metadata JSONB: cancel
  fan-out (§4) and the executions list filter need a queryable index;
  there is no metadata filter today and none is added.
- **`ports/` — the pre-declared rule-7 changes (all additive-optional):**
  1. `ports/queue.py` `RunQueueMessage.parent_run_id: str | None = None`
     (`extra="forbid"`; old payloads parse unchanged).
  2. `domain/events.py` `_Event.parent_run_id: str | None = None`
     (the envelope amendment this ADR declares).
  3. `ports/repository.py` `ExecutionRepo.list_runs` gains
     `parent_run_id: str | None = None` keyword (equality filter,
     the existing pattern).
  4. `domain/execution.py` `ExecutionContext.parent_run_id` and
     `RunResult.parent_run_id` (domain, listed here because the
     envelope and queue contract depend on them). Threading is
     verified-closed: `ExecutionContext` is constructed in exactly
     `worker._context` and `cli/main.py`; no resume path reconstructs
     it; `finish_run` never needs to write the column (the row exists
     from enqueue).

### 4. Budgets compose at the parent; cancellation fans out; the tree is clamped

- **Usage roll-up**: the sub-agent tool puts the child's `Usage` in
  `ToolResult.metadata["usage"]` (free-form, persisted in
  `tool_executions` — free auditability), and the runtime folds any
  tool-reported usage into `ctx.usage` right after `tool_runtime.execute`
  (`Usage.plus`). The orchestrator owns limits (ADR 0004): the parent's
  `RunLimits.exceeded` at the next iteration top fails the whole tree
  with `token_budget` — verified that no terminal can be reached
  without passing the checkpoint first, so nothing is needed before
  finalize. The child is separately capped by the same platform
  `RunLimits` on its own ctx; the tree total is clamped at the parent.
  The two-caps rule (platform vs per-agent snapshot) applies unchanged
  at every level.
- **Cancellation**: parent cancel (in-process token or cross-process
  `run_cancels` popped by the parent worker's heartbeat) reaches the
  blocked tool via the shared `CancellationToken` between stream
  batches → the tool cancels the child via `queue.request_cancel` and
  re-raises. The child dies at its own checkpoints. Cancelling the
  child DIRECTLY (it is an ordinary run) leaves the parent's wait to
  see `run.cancelled` and propagate honestly.
- Iterations compose the same way: a delegation is ONE parent
  iteration; the child's iterations are its own, capped by the child's
  platform + snapshot caps.

### 5. Children are non-interactive, bounded, and honestly flagged

- **Approval-gated tools inside a child are auto-declined, never
  paused.** The child's queue-message metadata carries
  `auto_decline_approvals: true` → `ctx.metadata` → the `_loop` gate:
  when set, every gated call takes the EXISTING decline branch
  (`ToolCallDeclined` + refusal tool message) without pausing, with
  parameterized copy — "This run has no human approver available, so
  the call was declined. Do not call this tool again for this request
  — continue without it and answer from what you know." (the S10
  decision record, an honest auto-decline — the child never pauses,
  so the parent's blocking wait can never strand on a pause frame).
- **Strategy `AskHumanStep` in a child is auto-answered**: when the
  flag is set, an ask appends a user message "No human is available in
  this run — proceed from what you know." and continues the loop (the
  resume-decisions pattern of appending a decision message;
  re-ask loops are capped by the ordinary iteration caps). The only
  two `_pause` sites are thereby closed for children.
- **Depth cap**: `ctx.metadata["sub_agent"]["depth"]` rides the queue
  message; the tool refuses (recoverable error `ToolResult`, never a
  terminal) to spawn beyond `JARVIS_SUB_AGENT_MAX_DEPTH`
  (Settings int, default 2: root=0 may spawn children, grandchildren
  allowed, great-grandchildren refused). Belt-and-braces beside §1's
  publish-time cycle detection.
- **Memory lint**: children run with `session_id=None` (the eval
  precedent), so a memory-enabled child silently runs memory-less —
  publish-time lint on the PARENT mirrors ADR 0015's `memory_ignored`.
- **`ToolRuntime` unbounded sentinel**: `timeout <= 0` (descriptor
  annotation OR binding config) disables `wait_for` entirely. Verified
  correction this ADR bakes in: `annotations={"timeout": None}` does
  NOT disable the timeout — `None` falls through to the 30s default
  (MCP calls today run under the default, not unbounded). Existing
  tools are byte-identical (no tool uses `<= 0` today); the sub-agent
  family's descriptors mint `timeout: -1`.

### 6. Handoffs: transfer with the conversation, expressed as a tool

A handoff is the model's control-flow decision mid-run — expressed as
a bound `handoff__<agent-name>` tool (strategy-agnostic: the existing
`function_calling` two-way branch needs no change), NOT a new strategy
step or runtime paradigm. At call time the tool:

1. Enqueues a **successor run**: ordinary `queue_message` +
   `create_queued_run`, `kind="agent"`, pinned target version (§1
   pins handoff targets at parent publish too), shared `trace_id` and
   `session_id` (the parent's, if any — so `/executions?session_id=`
   groups the chain), parent's remaining deadline, principal/tenant,
   `parent_run_id`, metadata `{"handoff": {"note": <arguments.note>}}`
   + depth.
2. **Transfers the conversation as rendered context**: the successor's
   `input` is the predecessor's transcript (`list_messages(parent_run_id)`,
   roles rendered as labeled text, truncated from the start to a
   char cap from Settings) + the handoff note. Explicit transfer, not
   session-sharing — verified decisive: conversations are unique on
   `(agent_id, session_id)`, so a DIFFERENT target agent would see
   none of the predecessor's messages by session alone. Recorded
   limitation: the successor's own memory/conversation starts fresh
   (per-agent keying); a same-agent handoff with memory enabled does
   continue the conversation through the ordinary memory path.
3. Returns `ToolResult` output "Handed off to <name> (run <id>)" with
   `metadata {"kind": "handoff", "successor_run_id": ..., "agent_id":
   ...}`.

**The runtime ends the predecessor at the handoff**: after the tool
batch, the loop sees the handoff metadata and returns
`LoopOutcome(kind="handoff", final_message=..., handoff=...)`;
`_after_loop` maps it to the ordinary `run.completed` terminal with
`final_message` naming the target and successor run (status
"succeeded" — no new terminal status, no new event type, the envelope
stays closed). Other calls in the same batch execute and persist
first; the handoff terminates the run at the end of the batch. The
linkage is queryable without any event-metadata change: the successor
row carries `parent_run_id` + `metadata.handoff`, and the executions
detail derives parent→successor links from the children query (§7).
Handoff descriptors are never approval-gated; handoff bindings join
the publish-time cycle graph (an A→B→A handoff loop is a cycle).

### 7. API surface and UI enablement

- `GET /v1/executions?parent_run_id=` — the new filter; the detail
  payload gains `children: list[RunResult]` (children query) and
  carries the run's own `parent_run_id` (via `RunResult`).
- `PATCH /v1/agents/{id}` — publish-time sub-agent/handoff pinning,
  cycle 422s, foreign/missing-target 422s; the agent detail gains a
  `lints` list (stale pins, memory-on-child) — lints, never failures.
- `GET /v1/capabilities` — the `agents` detail gains
  `sub_agents: true` and the `executions` detail gains
  `sub_agents: true` (parent/child links) — derived facts, flipped
  when the routes are real (the S4/S6/S11 pattern).
- UI (the roadmap's enablement line): the agent editor gains a
  sub-agent/handoff picker mirroring the MCP picker (agent select →
  bind `sub__`/`handoff__<name>` with `{agent_id}` config; the server
  stamps the pin); the executions detail gains a children section
  with links (sub-agent children and handoff successors, labeled) and
  a parent link on child details; the run console shows delegation as
  ordinary tool cards (the tool output names the child run).

### 8. Deliberately out of v1 (recorded, not silently dropped)

- **Parallel children** — a supervisor's batch executes sequentially
  and each delegation blocks; fan-out needs per-child waits and merged
  usage (the S6 §7 parallel-branches note anticipates the same shape).
- **Streaming child progress into the parent's event log** — the
  child's iterations are its own event stream; the parent's log shows
  the tool call. A `child.progress`-style relay is future work.
- **Message-role-faithful transcript seeding for handoffs** — v1
  renders the transcript into the successor's input (§6); a bulk-seed
  `messages` path (dual-keyed rows under the successor run id, the
  `_rebuild_messages` shape) is the recorded upgrade if flattened
  context proves lossy in practice.
- **A handoff-aware conversation surface** — `/v1/conversations` stays
  per-agent; the chain is visible via `?session_id=` / parent links.
- **Sub-agent/HITL composition** — children are non-interactive by
  construction (§5); an approval that pauses BOTH parent and child
  (pause the parent mid-tool on the child's pause frame, resume
  resumes both) is deferred with S13 in mind.
- **Cross-tenant sub-agents** — a sub-agent must be visible to the
  parent's tenant (shared NULL-tenant rows included, the
  `_shared_visible` pattern); no new sharing surface in S14.

## What stays frozen

- Terminal semantics: exactly one terminal per run, never raises,
  `run.awaiting_input` a segment end — children are ordinary runs and
  inherit all of it; handoffs end via the EXISTING `run.completed`.
- Every current event type's shape; the envelope's existing fields
  (only the optional `parent_run_id` is added, ADR-0003-amended here).
- The queue's claim/lease/sweep/ack contract (only the additive
  `parent_run_id` message field); the worker's claim path (children
  are `kind="agent"` — no worker branch at all, unlike S6).
- Agent runs' behavior and event sequences — no `sub__`/`handoff__`
  bindings resolves byte-identically (the §1 merged-tooling default).
- The error envelope, tenancy rules (D29), secret rules (ADR
  0005/0006 — no new credential surface), `ToolContext`'s shape
  (depth and flags ride existing `ctx.metadata`; the provider
  captures run-scoped values at resolve, §1).
- `ports/`: the ONLY changes are the four additive-optional members
  pre-declared in §3. Everything else rides existing Protocols.

## Consequences

- One blocking-wait surface to audit: the sub-agent tool's three
  non-terminal endings (§2) each produce an honest, bounded outcome —
  the parent can never block forever, and an orphaned child is fully
  visible and linked.
- The 30s-timeout trap is closed platform-wide by the §5 sentinel;
  existing tools are byte-identical (regression-gated).
- Publish-time pinning + cycle detection keeps the delegation graph
  static and acyclic; the depth cap is the runtime backstop. Stale
  pins are lints (D1 replay fidelity one level up, the D42 argument).
- Multi-minute delegations make the parent's SSE silent (frames only
  on events; the `PING` keep-alive exists in `sse.py` but no route
  sends it — a pre-existing gap worth fixing in S14's stream commit,
  noted here so it is not lost).
- Web: `parent_run_id` surfaces in the generated client after
  `make gen-api`; `WireEvent` types it automatically.
